Stage 01 · Planning

Scope & Architecture Planning

⏱ 2–3 days

Define what you're building and why, before writing code. This stage prevents the #1 cause of unfinished internship projects: scope creep.

◆ Objectives

  • Pick a project idea that maps cleanly to a real hiring use-case (job board, expense tracker, booking system, etc.)
  • Define the MVP feature set — the smallest version that's still demo-worthy
  • Draft the data model (entities, relationships) before touching MongoDB
  • Decide auth strategy, API structure, and folder architecture upfront

▤ Tasks

✦ Best AI Tools

Claude (Projects/Chat)Best fit

Strong at reasoning through data models, API design tradeoffs, and catching scope-creep before it happens — treat it like a technical co-founder, not a code generator.

Alt: ChatGPT (o-series for planning), Gemini
Excalidraw + AI pluginDiagramming

Fast ER diagrams and architecture sketches you can iterate on visually before locking the schema.

Alt: dbdiagram.io, Whimsical

✓ Best Practices

  • Cap MVP to 4–5 core features max
  • Design the schema before the UI, not after
  • Write API routes as a table before coding them

✕ Common Mistakes

  • Starting to code before the data model is settled
  • Copying a tutorial project 1:1 with no original feature
  • Skipping the README until the very end

▶ Prompt Example

I'm a final-year CS student building a MERN project for internship applications. My idea is [describe idea]. Help me: (1) narrow this to a realistic MVP with 4-5 core features, (2) design a MongoDB schema for the main entities with relationships, (3) list REST API endpoints as a table (method, route, purpose, auth required). Push back if the scope is too big for a 3-4 week solo build.

▣ Expected Outputs

Problem statement doc
ER diagram
API route table
GitHub repo + README skeleton

Stage 02 · Backend

Backend — Node, Express & MongoDB

⏱ 5–6 days

Build the API layer first so the frontend has something real to talk to. Getting auth and data validation right here saves rework later.

◆ Objectives

  • Stand up Express server with clean folder structure (routes/controllers/models)
  • Implement Mongoose schemas matching the Stage 1 ER diagram
  • Build auth (JWT-based signup/login, protected routes)
  • Implement CRUD endpoints with validation and error handling

▤ Tasks

✦ Best AI Tools

Claude CodeBest fit

Agentic terminal coding is ideal here — it can scaffold the full Express structure, write Mongoose models, and wire up JWT auth across multiple files in one pass while you review diffs.

Alt: Cursor, GitHub Copilot
Postman AI (Postbot)Testing

Generates test assertions and edge-case requests for each endpoint faster than writing them manually.

Alt: Thunder Client, Hoppscotch

✓ Best Practices

  • Never store plaintext passwords — bcrypt before save
  • Centralize error handling in one middleware
  • Keep .env out of git from commit #1

✕ Common Mistakes

  • No input validation on write routes (accepting anything)
  • Hardcoding JWT secret in source code
  • Skipping Postman testing and testing only via frontend later

▶ Prompt Example

Scaffold an Express + Mongoose backend for [resource, e.g. "job listings"] with: JWT auth middleware, a Mongoose schema matching this ER structure [paste schema], full CRUD routes with try/catch error handling, and Zod validation on create/update. Use a controllers/routes/models folder split. Explain any design decision that isn't obvious.

▣ Expected Outputs

Working Express API
Mongoose models
JWT auth flow
Postman collection

Stage 03 · Frontend

Frontend — React UI & State

⏱ 6–7 days

Build the interface that consumes your API. This is the stage recruiters actually screenshot, so polish matters as much as function.

◆ Objectives

  • Set up React (Vite) with routing and a clean component structure
  • Connect to backend API with a typed fetch/axios layer
  • Build core screens: auth, list view, detail view, form/create flow
  • Handle loading, empty, and error states everywhere data is fetched

▤ Tasks

✦ Best AI Tools

Claude (Chat/Artifacts) + Claude CodeBest fit

Use Artifacts to prototype individual components fast and visually, then Claude Code to integrate them into the real repo with routing and API wiring.

Alt: v0.dev, Cursor
v0.dev / Claude DesignUI prototyping

Fast for generating first-draft layouts you then refine with intentional design choices rather than accepting the default.

Alt: Galileo AI

✓ Best Practices

  • Design states before styling: loading / empty / error / success
  • Keep components small and single-purpose
  • Store only the JWT (not passwords) in memory/localStorage

✕ Common Mistakes

  • Only designing the "happy path" screens
  • Prop-drilling instead of context/state management when needed
  • Ignoring mobile responsiveness until the end

▶ Prompt Example

Build a React component for [feature] that calls this API endpoint [paste endpoint + response shape]. Include loading, empty, and error states with distinct UI for each — not just a spinner. Use Tailwind-free plain CSS matching a [describe visual style] aesthetic. Make it a single reusable component with clear prop types.

▣ Expected Outputs

Deployed-ready React app
Auth flow UI
Core CRUD screens
Responsive layouts

Stage 04 · Integration & QA

Integration, Testing & Hardening

⏱ 3–4 days

Connect frontend and backend end-to-end, then break it on purpose before anyone else does.

◆ Objectives

  • Full end-to-end flow working across auth + all CRUD features
  • Handle edge cases: expired tokens, network failures, bad input
  • Add basic automated tests for critical paths
  • Fix CORS, environment config, and cross-origin auth issues

▤ Tasks

✦ Best AI Tools

Claude CodeBest fit

Good at generating targeted test cases for edge conditions and finding integration bugs across the frontend/backend boundary when given both files.

Alt: Cursor, GitHub Copilot
Sentry / LogRocket (free tier)Debugging

Not AI-native, but pairs well with AI debugging — gives real error traces to feed back into Claude for fixes.

✓ Best Practices

  • Test the unhappy path as much as the happy path
  • Never deploy with console.log secrets left in
  • Keep a running bug list, don't fix ad hoc

✕ Common Mistakes

  • Assuming "it works on my machine" means it's done
  • No tests at all before deployment
  • Discovering CORS issues only after deploying

▶ Prompt Example

Here's my [controller/component] file: [paste code]. Identify edge cases I haven't handled (bad input, empty states, auth failures, race conditions) and write Vitest/Jest tests for the 5 most important ones. Then suggest minimal code changes to make those tests pass.

▣ Expected Outputs

End-to-end working app
Test suite
Bug log (resolved)

Stage 05 · Deployment

Deployment & Documentation

⏱ 2 days

A project only counts as a portfolio piece once it's live and explainable. This stage is where most student projects fall short.

◆ Objectives

  • Deploy frontend and backend to production hosts with a live URL
  • Set up MongoDB Atlas production cluster with proper access rules
  • Write a README that a recruiter can understand in 60 seconds
  • Record a short demo (video or GIF) of the working app

▤ Tasks

✦ Best AI Tools

Claude (Chat)Best fit

Strong for drafting a README that leads with the problem and outcome rather than a dry file listing, and for troubleshooting deployment config errors from pasted logs.

Alt: ChatGPT
Loom / ScreenStudioDemo capture

Quick, clean screen recordings for the README/LinkedIn demo without editing overhead.

✓ Best Practices

  • Lead README with what it does and why, not folder structure
  • Never commit real .env values, even to a private repo
  • Test the live deployed link yourself before sharing it

✕ Common Mistakes

  • README with no screenshots or live link
  • Free-tier backend spun down, live link times out on first load
  • Sharing the project without testing it in an incognito window first

▶ Prompt Example

Write a README for my MERN project [name]. It solves [problem] for [audience]. Tech stack: [list]. Key features: [list]. Structure it as: one-line hook, problem/solution, tech stack table, feature list with screenshots placeholders, local setup steps, and live demo link. Keep it recruiter-scannable, not a tutorial.

▣ Expected Outputs

Live deployed app
Recruiter-ready README
Demo video/GIF

Stage 06 · Presentation

Positioning for Internship Applications

⏱ 1–2 days

Turn the finished build into interview material — the project isn't done until you can defend every decision in it out loud.

◆ Objectives

  • Write resume bullets that lead with impact/decisions, not tech buzzwords
  • Prepare answers for "walk me through this project" and "why did you build it this way"
  • Publish a build-in-public post documenting the project honestly (including gaps)
  • Anticipate technical follow-up questions on architecture and tradeoffs

▤ Tasks

✦ Best AI Tools

Claude (Chat)Best fit

Good sounding board for mock interview Q&A on your own project — feed it your code/README and have it play skeptical interviewer.

Alt: ChatGPT

✓ Best Practices

  • Be honest about what you'd improve — it reads as maturity, not weakness
  • Quantify impact where possible (load time, test coverage, features shipped)
  • Practice the walkthrough out loud, not just in your head

✕ Common Mistakes

  • Memorizing a script instead of understanding your own code
  • Overclaiming ("built a scalable system") without backing it up
  • Not being able to explain a single architectural decision

▶ Prompt Example

Act as a skeptical technical interviewer reviewing my MERN project. Here's my README and key code: [paste]. Ask me 5 tough but fair questions about my architecture decisions, tradeoffs, and what I'd do differently — the kind a hiring manager would actually ask, not generic ones.

Key Decision Tree

Q: Which state management approach for the frontend?
Small app, ≤5 screens → useState/useContext, no library needed
Medium, shared state across many screens → Zustand (lightweight)
Large, complex data flows → Redux Toolkit
Q: Where to deploy the backend?
Free, simple, okay with cold starts → Render free tier
Need always-on for demos → Railway (small paid tier)
Want serverless functions → Vercel serverless / AWS Lambda
Q: How much AI-generated code is okay to submit?
Scaffolding/boilerplate → Fine, use AI freely
Core business logic → Write it yourself or heavily review/modify AI output
Anything you can't explain → Don't ship it — rewrite until you understand it

Wrap-up

Workflow Summary & Resources

◆ Workflow Summary

Six stages, ~3–4 weeks solo: plan the data model and API before coding, build backend before frontend, integrate and stress-test before deploying, and never ship a project you can't defend in an interview. AI tools accelerate scaffolding and boilerplate at every stage — the differentiator is understanding what they generate, not the volume of code produced.
